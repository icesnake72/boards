# verify-loop: 검증 루프 기반 코드 수정

빌드 + 전체 테스트 + 실제 기동 헬스체크를 통과할 때까지 수정을 반복하는 절차.
판정자는 `./scripts/verify.sh` (exit 0 = 통과, exit 1 = 실패)이다.

## 사용 조건

- **사용**: 보안 취약점 점검·수정, 인증/인가 로직 변경, "완벽히 대비되게 고쳐줘" 수준의
  결과 보증 요청, 여러 계층에 걸친 기능 수정
- **사용 금지**: 오타·주석·문서 수정, 이름 바꾸기 수준의 단순 리팩토링 — verify.sh 1회에
  빌드+테스트+기동 포함 1~2분이 걸리므로 낭비다

## 절차

1. **분석**: 요청을 분석하고 관련 코드를 읽는다. 보안 점검류 요청이면 취약 지점을 먼저
   식별하고 무엇을 어떻게 고칠지 정리한다.
2. **수정**: 코드를 수정한다. 동작 변경에는 그것을 검증하는 테스트를 함께 추가/수정한다
   (테스트는 H2로 돌므로 MySQL 불필요).
3. **검증**: `./scripts/verify.sh` 를 실행한다 (소요 1~2분, timeout 여유 있게).
4. **실패 시**: 스크립트 출력(gradle tail, 실패 테스트 목록, 앱 로그 tail)에서 원인을
   분석하고 2번으로 돌아간다. **최대 5회 반복** — 초과하면 중단하고 시도 내역·현재 상태·
   막힌 지점을 보고한다. 같은 원인으로 2회 연속 실패하면 접근 방식 자체를 바꾼다.
5. **통과 시**: 변경 요약과 함께 마지막 verify 출력(`=== VERIFY PASSED ===`)을 증거로
   제시하며 보고한다.

## verify.sh 동작 참고

- stage 1: `./gradlew build` (컴파일 + 전체 테스트, H2 기반 — 외부 의존성 없음)
- stage 2: MySQL(3306)·`.env`(KAKAO_SECRET/KAKAO_REST_API) 확인 — 미비 시 기동 검증은
  SKIP 하고 통과 처리된다. SKIP된 경우 보고에 그 사실을 명시할 것
- stage 3: `SERVER_PORT=8091 java -jar` 로 실제 기동 후 `GET /api/v1/boards` 200 확인
- 실패 원인 로그는 모두 stdout으로 나온다 — 별도 파일을 찾을 필요 없음
